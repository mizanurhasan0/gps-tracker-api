# Telegram messaging API

Admins send a direct message to guardians through Telegram. The admin picks one
or more vehicles. Every eligible guardian of those vehicles receives the message,
unless the admin narrows the list to specific guardians. Admins can also keep
reusable saved messages (templates).

This feature replaces the old SMS/WhatsApp deep-link screen in the mobile app.
The mobile client contract lives in
`android-app-vehicle-tracker/src/api/messaging.ts` and must match this file.

## Delivery model

- Each recipient gets an in-app notification through
  `NotificationsService.create()`. That call already queues a
  `telegram_deliveries` row (transactional outbox) when the guardian has a
  CONNECTED Telegram link, so the existing worker sends it with retries.
- Guardians without a Telegram link still receive the in-app notification. They
  are reported as `APP_ONLY`.
- The notification title is `business_settings.data.businessName` (trimmed). If
  that is empty, the title is `বার্তা`. Telegram shows `title\n\nbody`.
- A guardian with several children receives one message per send.

## Recipient eligibility

A guardian is eligible for a vehicle when they have at least one subscription
with `status='ACTIVE'` on a route with `active=1` whose `vehicleId` is that
vehicle, and the student is not archived. This matches the Notice `VEHICLE`
audience, plus the active-route filter.

## Endpoints

All endpoints require `@Roles('ADMIN')`. Timestamps are ISO 8601 strings. Text
inputs are trimmed before validation.

| Method | Path | Body / query | Response |
|---|---|---|---|
| GET | `/admin/message-templates` | none | `MessageTemplate[]`, newest `updatedAt` first |
| POST | `/admin/message-templates` | `MessageTemplateInput` | 201 `MessageTemplate` |
| PATCH | `/admin/message-templates/:id` | `Partial<MessageTemplateInput>` | `MessageTemplate` |
| DELETE | `/admin/message-templates/:id` | none | 204 |
| GET | `/admin/telegram-messages/recipients` | `?vehicleIds=<uuid>,<uuid>` | `TelegramRecipientsResponse` |
| POST | `/admin/telegram-messages` | `TelegramMessageInput` | 201 `TelegramMessageDetail` |
| GET | `/admin/telegram-messages` | `?page=1&pageSize=20` | `Paged<TelegramMessageSummary>` |
| GET | `/admin/telegram-messages/:id` | none | `TelegramMessageDetail` |

Unknown `:id` returns 404. `:id` is validated with `ParseUUIDPipe`.

### Validation

- `MessageTemplateInput.title`: 1–80 characters. `body`: 1–2000 characters.
- `vehicleIds` (query and body): 1–200 unique UUIDs. In the query string it is
  comma-separated. Unknown vehicle IDs return 400
  `One or more selected vehicles were not found`.
- `guardianIds`: optional. When present, 1–5000 unique UUIDs. Every ID must be
  eligible on at least one of `vehicleIds`, otherwise 400
  `Some selected guardians are not on the selected vehicles`.
- If the final recipient set is empty, 400
  `No guardians found for the selected vehicles`.
- `body`: 1–2000 characters.
- `templateId`: optional UUID, stored for history only. An unknown ID is stored
  as `null` rather than rejected.
- `requestId`: required UUID. It makes sends idempotent. The client keeps one
  `requestId` per draft and reuses it on retry, for example after a timeout. If a
  message with that `requestId` already exists, the server returns its
  `TelegramMessageDetail` with 200 and sends nothing. A concurrent duplicate
  that hits the unique index is handled the same way. When the existing message
  was created by a different admin, the server returns 409
  `This message request was already used`.
- `page` ≥ 1 (default 1). `pageSize` 1–50 (default 20).

## Types

```ts
export interface MessageTemplate {
  id: string;
  title: string;
  body: string;
  createdAt: string;
  updatedAt: string;
}
export interface MessageTemplateInput {
  title: string;
  body: string;
}

export interface RecipientGuardian {
  guardianId: string;
  name: string;
  phone: string;
  /** Active, non-archived children of this guardian on this vehicle, sorted. */
  studentNames: string[];
  telegramConnected: boolean;
}
export interface RecipientVehicle {
  vehicleId: string;
  name: string;
  plate: string;
  /** Sorted by name. Empty when the vehicle has no eligible guardians. */
  guardians: RecipientGuardian[];
}
export interface TelegramRecipientsResponse {
  /** Same order as the requested vehicleIds. */
  vehicles: RecipientVehicle[];
  /** Distinct guardians across all requested vehicles. */
  totals: { guardians: number; telegramConnected: number };
}

export interface TelegramMessageInput {
  vehicleIds: string[];
  /** Omit to send to every eligible guardian of vehicleIds. */
  guardianIds?: string[];
  body: string;
  templateId?: string;
  /** Idempotency key, a UUID generated by the client once per draft. */
  requestId: string;
}

export type TelegramMessageAudience = 'ALL' | 'SELECTED';
export interface TelegramMessageStats {
  /** Distinct guardians who received the in-app notification. */
  recipients: number;
  /** Telegram deliveries with status SENT. */
  sent: number;
  /** PENDING, SENDING, or FAILED with another attempt scheduled. */
  pending: number;
  /** CANCELLED, or FAILED with no further attempt. */
  failed: number;
  /** Recipients with no Telegram link at send time. */
  appOnly: number;
}
export interface TelegramMessageSummary {
  id: string;
  title: string;
  body: string;
  /** ALL when guardianIds was omitted. */
  audience: TelegramMessageAudience;
  /** Snapshot taken at send time, so renamed or deleted vehicles still show. */
  vehicles: { id: string; name: string }[];
  templateId: string | null;
  createdAt: string;
  createdBy: { id: string; name: string } | null;
  stats: TelegramMessageStats;
}
export type TelegramRecipientStatus = 'SENT' | 'PENDING' | 'FAILED' | 'APP_ONLY';
export interface TelegramMessageRecipient {
  guardianId: string;
  name: string;
  phone: string;
  status: TelegramRecipientStatus;
  sentAt: string | null;
  /** Last delivery error for FAILED rows, otherwise null. */
  error: string | null;
}
export interface TelegramMessageDetail extends TelegramMessageSummary {
  /** Sorted: FAILED, PENDING, APP_ONLY, SENT, then by name. */
  recipients: TelegramMessageRecipient[];
}
export interface Paged<T> {
  items: T[];
  page: number;
  pageSize: number;
  total: number;
  totalPages: number;
}
```

## Storage (migrations 15 and 16)

Migration 15 (`src/database/messaging.schema.ts`) creates the three tables.
Migration 16 (`src/database/messaging-request-id.schema.ts`) adds `requestId`.

- `message_templates`: id, title, body, `createdBy` (users, `ON DELETE SET NULL`),
  `createdAt`, `updatedAt`. Migration 15 seeds one row for each non-empty legacy
  SMS template in `business_settings.data`:
  - `paymentReminder` → `পেমেন্ট রিমাইন্ডার`
  - `absenceMessage` → `অনুপস্থিতি`
  - `delayMessage` → `গাড়ি দেরি`
  - `holidayMessage` → `ছুটির বার্তা`
  - `emergencyMessage` → `জরুরি বার্তা`

  The legacy keys stay in `business_settings` so older app builds keep working.
- `telegram_messages`: id, title, body, audience, vehicles snapshot (JSONB),
  `templateId` (`ON DELETE SET NULL`), `createdBy`, `createdAt`, and
  `requestId` (TEXT NOT NULL with a unique index, the idempotency key). Migration 16
  adds the column, backfills existing rows with `"requestId" = id`, then sets it
  NOT NULL.
- `telegram_message_recipients`: `messageId`, `guardianId`, `notificationId`,
  `telegramQueued` (whether a delivery row was queued at send time). The primary
  key is (`messageId`, `guardianId`).

Live stats come from joining `telegram_deliveries` on `notificationId`.

Sends run inside one `db.transaction()`, like Notices. External Telegram calls
never run inside the transaction. The outbox worker sends them afterwards. Each
send writes the audit action `TELEGRAM_MESSAGE_SENT`.

## Telegram link endpoint compatibility

`POST /telegram/connect` is the canonical method. Released app builds call it
with GET, so the server also accepts `GET /telegram/connect` with the same
handler.
